# ForgeFrame architecture

ForgeFrame has two runtimes: the **consumer** is the outer embedding app, and the **host** is the embedded iframe or popup. The package has two public entrypoints with named exports only: `packages/forgeframe/src/index.ts` (`forgeframe`) and `src/react.ts` (`forgeframe/react`, the React adapter). One library build emits both, so modules they share, such as the component registry and `ForgeFrameError`, are emitted once in a shared chunk and exist once per page; the root entry contains no React code. Importing either entrypoint does not start a browser runtime: a host starts only through `initHost()`. Without browser globals, `isHost()` returns false and a well-formed `initHost()` call returns null; malformed `initHost()` arguments still throw.

## Responsibilities and state ownership

Paths are relative to `packages/forgeframe/src`.

## Render and verified bootstrap

1. `create()` validates the declaration and registers a factory. Calling the factory constructs and tracks a consumer instance. Defining a component never starts a host, even in a window opened for its tag.
2. `render()` installs its render task before user callbacks can re-enter and places one render hold at the tail of the props queue. `performRender()` waits until earlier prop work has settled, rechecks cancellation, runs schema validation and then the component `validate`, and pins an absolute URL resolved against `document.baseURI` inside the URL-trust guard. It then resolves the container, emits `render`, and sequences the prerender, open, handshake, and completion stages. Updates requested during the attempt wait behind the hold and run in call order once it settles: after success they reach the host as PROPS after its INIT; after teardown they reject as closed, with the render's failure as `cause`; after a retryable failure (a URL or configuration error, or `POPUP_BLOCKED`) they apply locally. A second `render()` during the attempt joins it with the same arguments and rejects `VALIDATION` with different ones.
3. Cancellation is checked right after `render`, before any placeholder, iframe, or popup exists, so a listener that calls `close()` stops the render with nothing to tear down. Resource creation and user templates also check cancellation before advancing. ForgeFrame never calls props by name: instances have no built-in props, and only declared props are normalized and sent.
4. The renderer creates an iframe or opens a popup at the pinned URL. A function `url` always has a `hostOrigins` allowlist (`create()` requires it), so its resolved origin is checked against that allowlist before any resource exists; a URL that fails rejects `render()` with `ORIGIN_REJECTED` or `VALIDATION` and leaves the instance open for a retry. A static `url` without `hostOrigins` trusts its own origin, re-resolved against the document base at render. Origin checks and query/POST delivery policy use the same destination even if a template, event listener, or converter changes the document base. Query props are appended before any fragment without rewriting existing query bytes. POST navigation uses a hidden form whose methods are called through the mount document's form prototype, so named fields cannot shadow submission, append, or cleanup. Popup creation is synchronous within the opening workflow.
5. Protocol 3 `window.name` carries only channel metadata: the consumer uid, tag, protocol, context, and claimed consumer origin. The host reads it without rewriting it, so reloads and navigations keep the reconnect identity. A payload from another protocol makes `initHost()` throw a `VERSION_MISMATCH` upgrade error naming the consumer's ForgeFrame version, before any host state exists or anything is sent to that unverified consumer; in a window with no parent or opener there is no consumer to upgrade, so `initHost()` returns null instead. Each new host document creates a new session and requests current props through messaging; the host targets the directly readable consumer origin, or else the claimed one only when it is an exact HTTP(S) origin that passes the allowlist.
6. Consumer control handlers verify the opened window and configured origin policy before accepting bootstrap or INIT. During a render, bootstrap reads run inside the render hold, ahead of held updates; otherwise bootstrap waits behind pending prop work. It filters props against the browser-reported host origin, serializes current callbacks, and resets remote exports for reconnection.
7. The host validates incoming props, finishes readiness, and sends INIT with its session. If its schemas reject the props, it sends the verified consumer an ERROR marked `initFailed`, with the error's code; the host's `error` event and `ready` receive the same `ForgeFrameError`, with a non-ForgeFrame failure such as a throwing schema wrapped as `VALIDATION`. The consumer records it and keeps waiting, because the host can retry on the same page; a successful retry reports nothing, and a handshake timeout reports once as `INIT_TIMEOUT`, including the host's reason in its message and the host's coded error as its `cause`. Readiness rechecks destruction after bootstrap observers, then resolves to the live props object. With `autoInit: false`, INIT waits for `host.init()`; the consumer accepts host controls from the opened window before INIT, so the host can hide or resize itself first. Reading props never sends INIT. The consumer accepts the matching session, completes loading, and resolves `render()` before the single `rendered` event, so a listener may close the instance without failing the render. A blocked popup rejects with `POPUP_BLOCKED` and releases the attempt's resources without closing the instance; a window that only looked blocked is closed. Iframes keep their prerender swap animation. Popups remove transient loading content and the default wrapper and restore the original mount; custom container shells stay until normal teardown.

### Bootstrap details

- **Bootstrap response.** The consumer answers BOOTSTRAP with `{ props }` only; the host requires that object and ignores any other field. Nested rendering needs no wire support: a host imports a child component and renders it as a consumer, and the child page starts its own host with the parent host's origin in `consumerOrigins`. `children` stays a reserved prop name.
- **Start-up order.** `initHost()` checks its arguments (`init-host-arguments.ts`) before any environment check, then returns null without browser globals, throws while a host is active, reads the channel metadata, throws in the component form when the payload's tag differs, and checks the consumer origin selected for messaging against `consumerOrigins` before BOOTSTRAP. It never consults the registry for another definition, and nothing reconfigures a running host. After the bootstrap response, the coordinator checks the allowlist again as defence in depth. A failed start other than a schema rejection, such as a failed BOOTSTRAP request or an invalid response, is reported on the host `error` event as a `ForgeFrameError` with the failure's code and the failure as `cause`; a schema rejection reports its `VALIDATION` error there instead. `handshake-failure.ts` turns an unanswered BOOTSTRAP or INIT (a `CLOSED` acknowledgement timeout) into `INIT_TIMEOUT`. The host `error` event always carries an `Error`.
- **Retries.** A host is active from construction until it is destroyed or its start fails. A rejected `ready` releases the singleton before the caller's rejection handlers run, and `destroy()` releases it before destroying resources, so `initHost()` can start again on the same page; each attempt rereads the retained channel metadata from `window.name`. A tag mismatch or a disallowed origin leaves no active host.
- **Exports.** A host started from the component checks each `export()` against the component's `exports` schema before queueing it, so an invalid export rejects without being sent. The consumer decodes a verified EXPORT and validates it against the same schema before it replaces `instance.exports` and emits `exports`; an invalid export keeps the previous exports, emits a `VALIDATION` error, and answers the EXPORT with it, so the host's `export()` rejects with the same code. The host then releases that export's new callbacks; other delivery failures keep both batches, because the consumer may have stored the export. The schema validates only: exports are kept as received, and a schema that changes the value rejects it. The tag-agnostic host has no exports schema and sends unchecked.
- **Host teardown.** The bootstrap owner supplies the host's teardown callback. Destruction releases the singleton first, then destroys the transport, events, and props runtime. Teardown is idempotent, the callbacks clear only their own runtime, and destroying a stale host never affects a newer one.

### Loading and visibility

The renderer stores explicit iframe visibility separately from loading concealment:

- Eager frames use `display: none` while loading, so custom templates do not reserve space for both the iframe and the placeholder.
- Lazy frames use hidden visibility and keep their layout, temporarily clearing an inline `display: none` so GET/POST navigation can begin.
- Prerender completion checks current visibility before revealing the iframe, so a hide acknowledged during initialization stays in force.
- After the placeholder fades, the renderer restores configured display, visibility, opacity, and transition values and their CSS priorities.
- Caller-styled frames skip the default reveal animation, so configured concealment or opacity is never overridden. Explicit show/hide controls take precedence over configured visibility.
- A show requested before frame creation is applied when the frame is created, including lazy frames initially styled with `display: none`.

Iframe renders require a container attached to the document; the renderer rejects a detached one before creating resources and rechecks before navigation, so a `bodyParam` POST cannot open an untracked top-level window.

Popup resizing: browsers deny one origin access to another origin's window, so `instance.resize()` throws `VALIDATION` synchronously for a cross-origin popup without emitting `resize`. The consumer's `show()`, `hide()`, `focus()` and `resize()` only change this page, so they return `void` after their effects and events; `focus()` and `resize()` emit nothing with nothing mounted. `host.resize()` in a popup host resizes its own window, then sends RESIZE; the consumer resizes only iframes for host requests and notifies when the request took effect: the popup host resized itself while its window is still open, or a mounted iframe was resized (nothing is emitted when nothing is mounted or the popup has closed).

The iframe sandbox comes from the `sandbox` component option, decided by `resolveIframeSandbox` before the element factory runs: omitted gives `allow-scripts allow-same-origin allow-forms allow-popups`, a string is written as given (`create()` requires `allow-scripts` and `allow-same-origin` in it), and `false` writes none. `attributes` may not set `sandbox` in any letter case: `create()` checks static attributes and the element factory checks computed ones before an element exists. Popups are never sandboxed.

CSS encoding keeps case-sensitive custom property names and unitless numeric values; other numeric styles are pixels. Popup sizing converts numbers, numeric strings, and `px` strings to pixels. Other CSS units fall back to 500 pixels when opening, or to the current window size when resizing; iframe sizing passes CSS units through.

## Lifecycle and teardown

- Consumer teardown owns factory and index deregistration through the callback the factory passes to each instance; no public listener takes part. Deregistration runs before `closed`, the last event, after which the emitter is disposed: later subscriptions are accepted and never called.
- `close()` installs a shared completion promise before `close` is emitted, and destruction installs its own. Repeated and reentrant close requests wait for that operation, including deregistration and `closed`, without repeating cleanup or events. A close that arrives during failed-render cleanup waits for the destruction already in progress; that path emits `closed` without `close`.
- Each runtime's emitter is private. `instance.event` and the host's `on`/`once` are frozen facades that subscribe only to known names; removed v1 names throw with their replacement. Nobody outside the runtime can emit or remove another caller's listeners.
- Each handler has one registration per event, as with DOM listeners: registering it again keeps the first registration, and a returned unsubscribe removes only the registration it created, including a pending `once`.
- Event dispatch snapshots subscribed handlers and their registration identities before invoking them. Subscriptions added during dispatch wait for the next emission; listeners removed before their turn are skipped, including after cancellation and re-registration. A `once` observer can rearm itself without being invoked twice in one emission.
- `focus` is emitted only when a focus request reaches a mounted iframe or an open popup. `exports` is emitted after `instance.exports` is replaced by a verified EXPORT that passed the `exports` schema; a reconnection clears `exports` silently. The `cspNonce` component option reaches only templates, never props.

## Props update pipeline

`updateProps()` → serialized queue → isolated patch merge → schema conversion (which applies schema defaults) → self-acceptance checks (each schema accepts its own output unchanged) → component `validate` → URL/origin checks → snapshot commitment → optional host synchronization → prop notifications.

- **Presence and defaults.** The schema is the only source of a prop's presence, default, and value, in the direct and the wrapped form and on both sides. Normalization runs each defined prop's schema on the supplied value, including `undefined` for an omitted prop, so a schema that rejects `undefined` makes the prop required and the missing value fails with the schema's "Validation failed" message. No user code receives instance controls during construction.
- **Presence in patches.** `undefined` means "not supplied" in the factory input, update patches and React props. The patch merge deletes a key whose value is `undefined` from the raw input snapshot, so the raw snapshot never holds an own `undefined`. An update normalizes only the patched keys (every key while a construction failure is pending), so a reset key takes its schema default again, an optional one has no value, a required one rejects the update, and unchanged keys keep their normalized values. The normalized snapshot keeps every declared prop as an own key. Rechecks skip the keys the update has just normalized.
- **Deferred failures.** A schema failure during construction does not throw. The instance keeps a best-effort snapshot that is never delivered and rethrows the failure at render, at each trust boundary, and for updates until one normalizes every prop successfully.
- **Own properties.** Prop keys are read from own properties. Host validation treats omitted inherited names as missing, and reconciliation removes stale custom keys by own membership in the new snapshot. Shaped object schemas also read only own fields; omitted nested fields reach presence validation as `undefined`, including names inherited from `Object.prototype`.
- **Built-in schema rules.** String URL schemas accept parseable absolute HTTP(S) URLs, return the input unchanged, and compose with patterns. Number schemas accept only finite numbers, so JSON transport cannot turn them into `null`. Refinements accumulate as ranked checks instead of overwriting each other, so `.email().pattern()` and `.min(10).positive()` enforce both rules.
- **Undefined definitions.** Prop-definition entries set to `undefined` are dropped, so the prop is neither normalized nor sent, as for any undeclared input; a host drops a delivered field whose definition entry is `undefined`, as for an undeclared one. Declaration admission applies the same rule to reserved names; real definitions of host controls are rejected. Before registering a factory or creating a host runtime, `create()` and `initHost()` reject a getter- or setter-defined entry, or a wrapped `schema`, `deliverTo`, `sendToHost`, `queryParam` or `bodyParam` field that is an accessor or inherited (they are read again at normalization and delivery), a wrapped definition without a `schema`, one that sets a removed option (`serialization`, `required`, `default`, `value`, `decorate`, `hostDecorate`, `validate`, `alias`, `sameDomain`, `trustedDomains`, `outputSchema`) with an error naming its replacement, an invalid `deliverTo`, and a `queryParam` or `bodyParam` that is not a boolean or a non-empty name.
- **Defaults and outputs.** Callback schema defaults are factories that return the callback; the factory result is checked without invoking the callback. Optional and nullable presence carries through, and non-function defaults are evaluated directly; `prop.*` copies array, plain-object and `Date` defaults on each use, copying shared and cyclic references once, so instances never share them. A default removes `undefined` from a schema's output type unless the default can be `undefined`. Each prop has one schema, and each normalized value must pass that schema unchanged (`validateUnchanged`, shared by normalization, the consumer's rechecks and host validation). Normalization reports a violation as a definition mistake; trust boundaries recheck supplied inputs and normalized outputs, so a mutated input or output is caught before it is used. `prop.object`, `prop.record`, `prop.tuple`, `prop.union` and `prop.array` reject a missing nested schema when they are built.
- **Async schemas.** Unsupported asynchronous schema results are observed without being awaited. Validation, default, output, and nested-schema probes refuse them synchronously and do not produce unhandled rejections. Promise detection works across realms, including inside composite schemas.
- **Arrays.** Deliverable normalized arrays reject `undefined` entries and sparse holes before render resources are created or an update is committed. Delivery policy runs first, so local-only and withheld values are exempt. Custom JSON encoders run at delivery, and the arrays they return are checked then. Bridge guards stop `undefined` entries in delivered props and exports, including arrays a custom `toJSON()` returns, from becoming `null`. Item defaults are applied before these checks; standalone optional schemas are not affected.
- **Delivery policy.** One pure decision over the definition and the observed host decides delivery: a prop is delivered when `sendToHost` is not `false` and `deliverTo` is absent, is `'same-origin'` and the host is verified to share the consumer's origin, or is a matcher that admits the host origin. Bootstrap and updates use the browser-verified host; the initial query and POST body use the pinned URL's origin and treat the host as not yet same-origin, so `'same-origin'` props never enter the initial request. The host evaluates the same decision with its own origin and the verified consumer origin.
- **Parameters.** `queryParam` and `bodyParam` name the parameter (`true` for the prop key). Encoding is a data operation: dates become ISO strings, other objects JSON, and functions, `undefined`, `null`, invalid dates, and JSON-undefined objects are omitted.
- **Commitment.** Candidate preparation never replaces the current snapshot, so validation or origin failures leave the previous snapshot intact. Commitment happens before host synchronization; a transport failure does not roll back the committed consumer state.
- **Queue.** Queue entries are installed before schema transforms or the component `validate` can re-enter, including before a host connects. The first update outside a render hold starts synchronously; later entries run in FIFO order, and a failure does not block later entries. Host bootstrap and updates share the queue, so bridge batches never overlap. A render attempt's hold is one more entry: updates admitted after it wait without running user code, the render's own bootstrap reads run inside it, and it releases once when the attempt settles. Teardown abandons the queue tail and releases the hold, so every held update settles.
- **Host side.** The host deserializes, validates each expected prop with the same schema the consumer used (a value the schema rejects or changes rejects the snapshot), and filters before reconciling. Stale keys are removed from the live props object, and `then` and `children` are dropped from every snapshot, so an unchecked consumer cannot make it a thenable. `host.onProps` is the only way to observe updates, and it returns an unsubscribe function. Subscriber registrations are snapshotted after commitment: new or re-registered observers wait for the next update, and cancelled registrations are skipped. Unsubscribe functions capture their registration token, so a stale handle cannot remove a later registration of the same callback. Async subscriber failures are caught without awaiting subscriber work or delaying acknowledgement. A newer acknowledged update that arrives during bootstrap wins over the older bootstrap snapshot. Updates acknowledged before bootstrap completes are committed without notifications; bootstrap then publishes the final snapshot once. The props object `ready` resolves to keeps its identity; each `onProps` notification receives the new snapshot.

### Consumer-only and withheld props

The host expects only the props delivered to it: it drops definitions that set `sendToHost: false` and those whose `deliverTo` excludes its origin, using its own origin (read when the host starts) and the verified consumer origin. Fields for the other definitions are discarded before decoding bootstrap or update snapshots, including values sent by stale or misconfigured consumers, so they never enter host state or notifications. Every expected prop is validated with its output schema, or its schema, present or not; withheld props are neither required nor accepted. Consumer validation still applies every definition. Undeclared fields, including those of `undefined` definition entries, are discarded the same way. Only a tag-agnostic host started without `props` keeps every field, unvalidated; the component form always has definitions, empty for a component without `props`.

Host definitions are fixed when `initHost()` starts the runtime. A pending bootstrap selects the latest acknowledged wire snapshot and filters it with those definitions before commitment, so consumer-only and withheld fields cannot return.

## Serialization

- **Cross-realm values.** Neutral realm-value helpers recognize genuine `Date` internal branding and ordinary object prototypes across windows. Schemas, output comparisons, array admission, and recursive codecs share these helpers. Class instances are not ordinary records.
- **JSON conversion.** Props and exports cross as JSON through the function bridge. Each object other than an array, a `Date`, or native raw JSON converts once, as native JSON does: a callable `toJSON(key)` with its original receiver, then primitive-wrapper unboxing. Fields and getters are read once, so `Date` encoders run once per occurrence. A native JSON probe with an empty property list unboxes boxed primitives without enumerating ordinary records or running exception-driven brand checks; custom coercion hooks, foreign wrappers, and `BigInt` rejection behave as in native JSON. Native raw JSON, recognized by its brand even from another realm, passes through unchanged, so the message's JSON encoding writes its text and the receiver parses the value it represents.
- **Snapshots of caller data.** Bridge array encoding captures indexed entries once during presence admission, regardless of the array's prototype or overridden methods, and encodes that snapshot, so getters cannot introduce unchecked `undefined` entries on a second read. Object schema shapes, tuple item arrays, union branch arrays, and enum value arrays are shallow-copied at construction; later caller mutation cannot change an established schema, its diagnostics, or its presence clones.
- **Event payloads.** Each event's payload type comes from one event map (`ComponentEvents` for instances, `HostEvents` for hosts), and handlers are removed only through the function their registration returned.

## Messages and remote callbacks

Admission rejects self-sent and untrusted traffic before decoding, then checks channel identity and a usable event source. Responses must also match the pending request's target window and expected origin. Request handlers receive browser-verified source metadata, not the metadata claimed in the envelope.

The request integration runs the handler, builds a response, and posts it. A request with no handler is answered with `VERSION_MISMATCH`, so a peer on another version fails fast instead of at its timeout. Every outgoing message is JSON-encoded through `stringifyForWire`, so an unencodable value such as a `BigInt` rejects as `VALIDATION` with the encoder's error as `cause`. If the result cannot be serialized, an error response is sent instead. An error response carries the `ForgeFrameError` code of an error ForgeFrame raised, and the receiver rebuilds a `ForgeFrameError` for a known code. A remote callback's own failure is sent without a code, even when it is a `ForgeFrameError`, so callers receive a plain `Error`; the exception is a relayed remote wrapper the bridge itself created (a peer's export registered by the consumer's relay), whose own failure, such as `CLOSED`, keeps its code. Timeouts and teardown reject pending requests. Remote callback calls (CALL and PEER_CALL) have no timeout, because the callback may still be running in the other window: they settle with its result, or reject on teardown or, for consumer calls, when the host reconnects with a new session. A props update sent to a host document that was replaced also rejects with `CLOSED` when the new session's BOOTSTRAP arrives, instead of at the acknowledgement timeout; the new session reads the current props. Host teardown posts a one-way TEARDOWN notice; the consumer then rejects its calls to that window, including calls the host never dispatched, and rejects later calls until the host starts a new session with BOOTSTRAP or INIT. While calls to a window are pending, the bridge checks every 10 s that the window still answers on a separate liveness channel; an unanswered check rejects them, which covers documents that go away without teardown, such as a navigated iframe or an unloaded consumer page.

Messenger requests encode the full envelope before allocating a pending request and signal the delivery attempt immediately before posting. Prop and export batches abort newly registered callbacks when encoding fails before that point, and conservatively keep them after a post was attempted. Unknown thrown values are normalized without letting diagnostic coercion throw, so callback errors always reach the response path.

The function bridge:

- **Identity.** Local functions get stable IDs while retained. Remote wrappers are cached by ID, window, and origin; the remote cache evicts beyond 500 entries. Local callable references are never evicted to admit another callback.
- **Capacity.** Each prop or export snapshot admits at most 500 distinct functions. New registrations are staged and callable during delivery. An update batch removes stale references once acknowledged; a bootstrap batch completes as soon as serialization finishes. A serialization failure before delivery rolls back only new registrations. A delivery failure conservatively keeps previous and possibly delivered references in a pool capped at 1,000 and rejects further registrations until an acknowledged retry with retained callbacks or a new session frees capacity.
- **Reconnection.** The verified new-session reset runs inside queued bootstrap serialization after earlier updates settle. It releases callable registrations but keeps weak IDs, so callbacks the new host already acknowledged keep their identity when re-registered. Teardown clears both registrations and weak IDs.
- **Peer relay.** Peer exports go through a separate `PEER_CALL` relay bridge with the same source checks. Selection is pure policy over peer facts observed from each indexed instance. Discovery takes the requester's uid and tag from the consumer instance rather than the request, and is opt-in on both sides: a requester whose component has no `peers` option is refused with a `VALIDATION` error, and only components that set `peers` are listed. It returns only peers whose verified host origin equals the requesting host's browser-reported origin, including with `allTags`; a peer's `peers` matcher may admit other requesting origins. Opaque (`"null"`) origins are distinct from one another, so an opaque requester receives no peers and a peer whose own host is opaque is never listed, even when its matcher matches; the messenger never admits an opaque sender, even under `'*'`. A peer whose host is still loading is matched by the origin the consumer opened it at and listed without exports; instances that were never opened are omitted. Discovery uses append transactions with a cumulative 500-reference bound; a failed serialization rolls back the additions without retiring held peer snapshots. Held snapshots survive prop batches and repeated discovery; replacement exports retire their original source functions. Reconnection clears old requester relay identities, and teardown clears both bridges.
- **Codec.** Props and exports share one recursive bridge codec. Codec guards require the complete own-property shape of transport wrappers. Encoding escapes ordinary records shaped like function, `Date`, or escaped-record markers, including the escaped-record marker itself, after their fields are converted, so a custom `toJSON()` that produces a marker shape still arrives as data. Marker fields written as native raw JSON count as the value their text represents. Codec-generated function and `Date` markers keep their identity, and decoding restores escaped fields as data rather than as a function or `Date`. Serialization handles `Date` framing, cycles, and unsafe-key filtering, converts objects other than arrays, dates, and native raw JSON through `toJSON(key)` and primitive unboxing once, and reads arrays entry by entry; decoding reconstructs function references and `Date` wrappers together. These encoding callbacks run inside the transport-owned serialization batch.

## React commit flow

The hook wrapper updates callback refs, mounts an instance for the current context, moves the `instanceRef` handle to a changed `instanceRef` prop, and observes committed props, in that effect order. The container element's ref is a callback created once per forwarded ref, so React attaches and forwards the element during commit, before layout effects, and a forwarded callback's React 19 cleanup replaces its `null` call.

`instanceRef` receives a frozen handle (`uid`, a live `exports` getter, `event`, `close`, `focus`, `resize`, `show`, `hide`; no `render` or `updateProps`) only after the current mount's `render()` resolves, immediately before `onRendered`. It is cleared before `onClose` when that instance closes (by the host, the user, the handle or cleanup), when the wrapper unmounts or `context` remounts it, and is never set after a failed render. Only the current mount writes it; a callback ref's React 19 cleanup replaces its `null` call, and a callback ref that throws is logged like the other wrapper callbacks, so `onRendered` and `onClose` still run. A render failure that also arrives on the `error` event is reported to `onError` once.

Each mounted instance has its own sync state. Commits produce shallow snapshots without `undefined`-valued keys, so passing `undefined` and omitting a prop are the same commit, and send `undefined` for previously known keys that are now omitted, which resets them in core. A failed equivalent pending commit requests one retry; successful acknowledgements advance the FIFO. There is no render gate: a commit during `render()` is sent at once and the core holds it until the render settles; if the render fails, the held update's `CLOSED` rejection is not reported, because the render failure is. Draining checks the current instance identity around every await, so failed or obsolete work cannot update a new mount's refs or queue. Cleanup deactivates the queue before closing and unsubscribing.

## Playground

### Company demo

The consumer's `/company` route is a fictional Pip Veterinary invoice portal; the host's `/payment.html` entry is the fictional Harbor Pay provider. The shared [payment contract](../packages/playground/payment/contract.ts) defines invoice data, the simulated outcome, and the remote readiness and result callbacks. Its amount schema requires nonnegative safe-integer AUD cents at consumer admission and at host initialization and updates, even when a custom consumer validates more loosely. The consumer restricts the provider origin; the provider starts with the tag-agnostic `initHost({ props, consumerOrigins })` form and the shared definitions, so its bundle omits the consumer runtime, and reads props from `ready`. A build-time define that only the browser tests set exposes those props on a namespaced test global; production builds drop it.

State is split by application. The consumer owns invoice selection, session identity, payment receipts, and reset. The provider owns card inputs, form validation, a short simulated processing delay, and decline/retry state. Only receipt metadata crosses back to the merchant.

- **Outcomes.** The first declined attempt leaves the invoice unpaid; a retry approves in the same provider window.
- **Merchant acceptance.** Callback arguments are treated as unknown. The merchant validates the discriminator and every receipt field (safe-integer cents, a valid ISO timestamp, four masked digits), matches the invoice and amount, then commits its own snapshot. Malformed results leave the invoice unpaid and allow a valid retry. These rules live in the browser-independent `consumer/company-demo/acceptance.ts`.
- **Provider acknowledgement.** The provider treats callback return values as unknown and requires the matching status and the invoice captured in its submitted result: `declined` before showing decline/retry feedback, or `recorded` before marking approval and closing. A malformed or mismatched acknowledgement leaves the payment window open with recovery guidance. Outcome, card-number, and acknowledgement rules live in `payment/simulation.ts`; the provider passes clock and randomness observations into receipt construction.
- **Cancellation.** Closing marks the session cancelled, and destroy releases the merchant UI after cleanup. Callbacks from cancelled or replaced sessions cannot commit a payment.
- **Focus.** Native dialogs confine modal focus; the provider handles Escape for focused iframe inputs.

Application entry points compose these rules with DOM presentation and ForgeFrame calls.

Experience and Technical are presentation modes of the same consumer application. The Technical panel observes callback call sites and local return values; it opens no separate communication channel. Its five-step guide records the actual render, readiness callback, result, local acknowledgement return, and destroy for each invoice, and separates payment outcome from window lifecycle. Source tabs lazily import the authored consumer, host, shared contract, and both rule modules when Technical is first opened; their TSDoc explains the integration boundaries. A source-loading failure never blocks payment. Browsers cache failed module imports, so the recovery guidance asks for a page refresh and warns that refreshing resets the sample invoices.

Consumer builds generate static entry pages for `/company` and the test routes. Host builds include the payment entry separately from the diagnostic host. `VITE_HOST_URL` sets the provider address; `VITE_CONSUMER_URL` sets the payment host's consumer allowlist. All payment processing and seed data are fictional and reset without persistence.

### Diagnostic playground

Host displays and consumer logs build dynamic content with DOM text properties, keeping peer-controlled strings out of HTML parsing. Static layouts and controls are authored markup.

## Design rules

Operations implement cohesive policy, transformations, state transitions, or browser actions. Integrations sequence package-owned behavior. A call to a browser, runtime, or schema API does not by itself require extraction. Keep cohesive recursive algorithms and short local adapters together; do not add an interface or wrapper without a useful responsibility.

Pure policy depends on supplied observations and neutral types and helpers. Browser reads and resource effects belong in browser operations or their coordinating runtime. Internal helpers stay inside their subsystem and are not added to root exports. Schema classes are exported as types only, so `prop.*` is their one constructor; they keep their existing members, decomposed with module-level helpers. `CONTEXT` and `EVENT` are internal constants; the public names are the `ContextType` and `EventType` literal unions.

See the [callable reference](iosp-review.md) for per-callable classifications and the [test index](../packages/forgeframe/tests/README.md) for boundary tests. Public contracts are documented in the root README and enforced by the typecheck suites.
